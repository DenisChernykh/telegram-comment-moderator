# Free tier budget — проверено 17–18.10.2026

Используются только **Workers Free** и **SQLite Durable Objects Free**. Платного
inference API, OpenAI API key, Queues, KV, R2, D1, Redis и Cron в проекте нет.
MCP Events запускает ChatGPT в рамках доступности и лимитов аккаунта ChatGPT;
это отдельное ограничение, не часть квоты Cloudflare.

## Вариант без зависимости от квоты ChatGPT — исследование 18.10.2026

Workers AI доступен на Workers Free с отдельным бесплатным бюджетом
**10 000 Neurons/сутки**. При его исчерпании запросы Free завершаются ошибкой;
превышение требует отдельного перехода на Paid. Сброс — 00:00 UTC, то есть
05:00 Екатеринбург. Некоторые модели требуют платного billing даже до этого
порога, поэтому произвольный выбор модели недопустим.
Источник: [Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/),
страница обновлена 15.10.2026, прочитана 18.10.2026.

Конкретное предложение: перенести смысловой анализ из событийного Work в
ограниченные Alarms существующего DO через Workers AI binding; оставить MCP
для контроля владельца. Кандидат для проверки — @cf/qwen/qwen3-30b-a3b-fp8,
указанный в бесплатной таблице: 4 625 Neurons/млн входных и 30 475/млн выходных
токенов. Это кандидат, не проверенная для русского спама модель. Количество
комментариев в сутки нельзя приравнивать к Neurons: нужны замеры полного
policy/context, вывода, повторов и общего использования аккаунта.

Перед переключением: проверить качество на сохранённой отдельной выборке,
измерить расход, ограничить вход/выход, попытки и суточный бюджет. Решения
должны проходить прежние scope/revision/epoch/deadline и защитные проверки;
недоступность модели, невалидный ответ и неясность не разрешают удаление.
При смене исполнителя нужен один источник решений без параллельного монитора.
Это убирает зависимость от квоты ChatGPT, но не даёт бесплатной безлимитности.

**Статус: только предложение.** В AGENTS.md по-прежнему запрещён inference API;
для Workers AI нужно явное исключение владельца. Binding, модельные вызовы,
передача комментариев новому обработчику, deploy и смена исполнителя не сделаны.
Платный тариф и автоматическое увеличение бюджета не предлагаются.

## Проверенные квоты

| Ресурс | Настоящий Free | Источник |
|---|---:|---|
| Worker HTTP requests | 100 000/сутки | [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) |
| Worker CPU HTTP и Cron | 10 мс/вызов | тот же источник |
| SQLite DO requests, включая Alarms/RPC | 100 000/сутки | [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) |
| DO duration | 13 000 GB-s/сутки | тот же источник |
| SQL rows read | 5 млн/сутки | тот же источник |
| SQL rows written | 100 000/сутки | тот же источник |
| SQLite DO storage | 5 ГБ на аккаунт, 1 ГБ/объект | [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/) |
| DO active CPU | default 30 секунд/вызов | тот же источник; это **не** CPU внешнего Worker |
| Queues, только для сравнения | 10 000 операций/сутки; 24 ч хранения | [Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/), [limits](https://developers.cloudflare.com/queues/platform/limits/) |
| D1, только для сравнения | 5 млн read / 100 000 write rows/сутки | [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) |

Один setAlarm — одна записанная строка. DELETE тоже write; изменения индексов
увеличивают учёт строк. D1 не даёт большего бесплатного SQL-бюджета: DO выбран для
координации, сериализации и Alarms. Для Queue небольшой event обычно стоит
write + read + delete = три операции. sendBatch/consumer batch не превращают
пакет в одну операцию; повторная доставка добавляет операции.

## Модель нагрузки

Это консервативный расчёт для планирования, **не результат production benchmark**.
N — новых комментариев/сутки; E=1.2N — с 20% содержательных редактирований;
U=1.05E — с 5% повторных Telegram updates. S=1 подходящая подписка на ревизию;
T=1.1E — попытки event delivery с 10% повторов. P=0.1E — spam-решения;
D=1.1P — попытки удаления. MCP на ревизию: context + verdict, batch=1.
Обе подписки created/updated с одинаковым callback не удваивают S: событие
имеет одно имя. Дублирующие мониторы увеличивают S и расходы.

Оценки учитывают дедупликацию, inbox, root/parent context, решения, SQL indexes,
claim/finish, watchdog/final alarms и амортизированную очистку:

- Worker requests ≈ U + 2E + 100 = 3.66N + 100 (плюс OAuth, ручные чтения и злоупотребления).
- DO requests ≈ Worker requests + T + D + E + 100 = 6.312N + 200.
  Это верхняя оценка при почти одном alarm на операцию; batching уменьшает requests.
- SQL writes ≈ 90N + 2 000. Внутри: admission ~14E, delivery ~9T,
  decisions ~10E, deletion ~10D, cleanup ~12E и резерв на watchdog/индексы.
- SQL reads ≈ 450N + 10 000 при индексированных due/deadline/expiry и коротком контексте.
  Частый вызов полного status, большие inbox-списки и несколько подписок увеличат расход.
- При callback RTT 1 с и Telegram RTT 1 с DO active duration примерно
  0.128 × (T×1 с + D×2 с + локальная работа) GB-s. Сетевое ожидание не является CPU,
  но входит в активное wall time DO. При постоянной активности одного объекта
  верхняя оценка за сутки: 86 400×0.128≈11 059 GB-s.
- Storage ориентировочно N×1.2×7×12 KiB текста/контекста/индексов плюс
  N×1.2×30×1 KiB компактного аудита; зависит от UTF-8 и фактических индексов.

| Новых/сутки | Worker requests | DO requests | SQL writes | SQL reads | Плановый storage | Вывод |
|---:|---:|---:|---:|---:|---:|---|
| 100 | ~466 | ~831 | ~11 000 | ~55 000 | ~14 МиБ | Большой запас при одном мониторе |
| 1 000 | ~3 760 | ~6 512 | ~92 000 | ~460 000 | ~134 МиБ | SQL writes почти исчерпаны; без измерений и запаса аккаунта не обещается |
| 5 000 | ~18 400 | ~31 760 | ~452 000 | ~2.26 млн | ~668 МиБ | Не помещается в Free по SQL writes |

Модель чувствительна к числу редактирований, индексов и попыток. Даже 1 000/сутки
может превысить Free. Это не SLA и не гарантия пропускной способности.
Default admission cap — **500 updates/сутки**, включая редактирования, повторы с
новым update_id и полученные корни. Он оставляет запас под остальные операции;
владелец может настроить 1–5 000, но увеличение не повышает квоты Cloudflare.

17.10.2026 перед deploy в выбранном аккаунте UI показал Free, 0/100 000 requests,
0 CPU и отсутствие проектов; API список Workers был пуст. Это снимок текущего
аккаунта, а не резерв квот. Новые проекты в том же аккаунте делят эти лимиты.
Другие Cloudflare аккаунты не следует смешивать при расчёте.

## Ограничения и остановка

Inbox ≤20 000 записей; audit ≤30 000; ≤5 групп; ≤10 subscription identities;
≤4 work operations/alarm; ≤5 попыток с backoff и retry_after, lease 60 с.
Webhook/MCP input ≤64 KiB, tool structured output ≤48 KiB, batches ≤10 решений,
pending page ≤20. Большой ответ MCP требует уменьшить limit. Контекст ограничен.
Тексты/полученные updates/корни — 7 дней, компактный аудит — 30 дней;
очистка до 25 строк на таблицу за alarm. Pending ожидание ограничено 30 минутами,
настраивается от 1 минуты до 6 часов, всегда раньше 48-часового предела Telegram.

При превышении admission cap webhook возвращает 503: Telegram может повторить
доставку. После 24 часов недоставленные updates могут быть потеряны. Если сама
Cloudflare Free квота закончилась, операции завершаются ошибкой до сброса в
00:00 UTC (05:00 Екатеринбург). Не принятый update не подтверждается успешным
ответом. Если решение/удаление не удалось, комментарий остаётся; платный fallback
и повышение тарифа отсутствуют. Никакой гарантии восстановления пропущенной
истории Telegram или MCP protocol replay нет.

## Измерения

Сборка сообщает Worker Startup Time, но эта цифра не доказывает CPU HTTP-запроса.
Локальные тесты workerd и wall time запросов также не доказывают лимит 10 мс.
Фактические remote измерения и ограничения приёмки записаны в
[docs/VERIFICATION.md](docs/VERIFICATION.md). Перед увеличением cap нужны
production CPU, SQL rows и active wall time по реальному распределению запросов.

В ранней live-выборке 17.10.2026 один настоящий edited_message вернул 200,
но tail показал 12 мс CPU внешнего Worker — выше номинальных 10 мс Free.
После исправления gateway два подтверждённых первых запроса разных изолятов
показали по 2 мс; 10 повторных проб — 0–1 мс. Настоящий Telegram-комментарий,
создавший job и событие, также дал 2 мс внешнего CPU (DO отдельно: 4 мс).
Реальное редактирование, завершившееся автоматическим удалением, — 3 мс
(DO: 2 мс). Analytics за окно 10:34–10:42 UTC: 46 успешных запросов, 0 ошибок,
CPU P50=1,067 мс и P99=3,313 мс внешнего Worker.
Это измерения конкретной выборки, не гарантия любого будущего cold start.
Данные и границы сопоставления находятся в VERIFICATION.
